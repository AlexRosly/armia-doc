Ниже — **реально выполнимый roadmap на 3 спринта** с приоритетами, критериями готовности и поэтапной миграцией от текущей disk-oriented схемы к RAM/tmpfs-first.

# Цель
Свести к минимуму попадание чувствительных данных на постоянный диск и сократить окно хранения до **максимум 10 минут**, при этом сохранить работоспособность текущего сервиса.

---

# Спринт 1 — “Быстрое усиление без ломки архитектуры”
**Задача:** резко поднять безопасность на текущем коде и инфраструктуре, не переписывая генерацию целиком.

## 1) Лимиты и безопасный прием запросов
- Зафиксировать `MAX_INPUT_SIZE = 1 MiB`
- Одинаково выставить:
  - Nginx: `client_max_body_size 1m`
  - Node/Express JSON parser: `limit: '1mb'`
  - серверная валидация
  - при возможности — фронтовая подсказка до отправки

**DoD**
- Запрос > 1 MiB получает `413`
- Валидные запросы до 1 MiB проходят

---

## 2) Nginx: не писать request/response на обычный диск
Для **маршрутов генерации**:
- `client_body_buffer_size 1m`
- `proxy_request_buffering off`
- `proxy_buffering off`
- `proxy_http_version 1.1`
- `proxy_max_temp_file_size 0`
- temp paths Nginx направить в `tmpfs` как страховку

**DoD**
- Нет temp-файлов Nginx на обычном диске при генерации и скачивании
- Проверено на запросах ~100KB / 500KB / ~1MB

---

## 3) Безопасное логирование
- Убрать из логов:
  - body
  - response body
  - все headers целиком
  - cookies / authorization
  - query/params с пользовательскими данными
- Оставить белый список:
  - `requestId`
  - method
  - route
  - status
  - duration
  - response size
  - technical error code
- Выключить `X-Powered-By`

**DoD**
- В логах нет текста пользователя и чувствительных заголовков

---

## 4) Один активный job на пользователя
- На backend ввести правило:
  - **1 пользователь = 1 активная работа**
- Второй запрос в активный период → `409 Conflict`
- Освобождение после:
  - early close
  - ошибки
  - TTL cleanup

**DoD**
- Два параллельных запроса одного пользователя не проходят

---

## 5) Общий лимит одновременных генераций
- Ввести `MAX_CONCURRENT_JOBS`
- При достижении:
  - либо короткая ограниченная очередь
  - либо controlled reject “server busy”

**DoD**
- При нагрузке сервер не запускает безлимитные генерации

---

## 6) Надежный lifecycle: `expiresAt` — главный
- Источник правды только backend
- Frontend лишь показывает остаток времени по `expiresAt`
- Cleaner по `expiresAt`
- Cleanup идемпотентный
- После рестарта cleaner подчищает просроченное

**DoD**
- Early close удаляет сразу
- Без close — удаление максимум через 10 минут
- После рестарта backend просроченные jobs чистятся

---

## 7) Перенести `storage/` в tmpfs
Не переписывая логику файлов сейчас:
- `storage/docx`
- `storage/pdf`
- `storage/armdoc`

размещаются в RAM-backed FS (`tmpfs`).

**Это ключевой компромиссный шаг**: код почти не меняется, а физически данные уже не лежат на постоянном диске.

**DoD**
- Документы создаются и скачиваются как раньше
- Но `storage/*` — в RAM/tmpfs, а не на обычном диске

---

## 8) Проверить PDF-конвертер
- Проверить `convertToPdf(...)`
- Выявить, пишет ли он:
  - temp files
  - user profile
  - `/tmp`
  - служебные артефакты
- Если пишет — тоже перевести temp path в tmpfs

**DoD**
- Понятна карта временных файлов PDF-конвертера
- Все временные каталоги либо отключены, либо RAM-backed

---

## 9) Swap / dumps / snapshots
- Отключить или зашифровать swap
- Выключить core dumps
- Запретить heap snapshots / diagnostic reports в production
- Проверить PM2/systemd, чтобы не писали дампы с памятью

**DoD**
- Нет штатных memory dumps на постоянном диске

---

## 10) Read-only код и минимальные права
- backend не под root
- код и шаблоны read-only
- приложению разрешена запись только туда, где реально нужно (tmpfs)

**DoD**
- Процесс приложения не может менять собственный код и шаблоны

---

## 11) Egress deny
- Если backend не нужен внешний интернет:
  - запретить исходящие соединения по умолчанию
  - разрешить только Mongo/локальные внутренние сервисы при необходимости

**DoD**
- Тестовая попытка отправить данные наружу из backend блокируется

---

## 12) Базовый FIM/monitoring
- Вынести FIM/monitoring на внешний узел, если возможно
- Начать контролировать:
  - backend
  - frontend
  - шаблоны
  - nginx config
  - env/config
  - package-lock
  - systemd/pm2

**DoD**
- Изменение тестового файла вызывает alert

---

## Результат спринта 1
Без сильной ломки кода вы получите:
- безопаснее логирование
- жесткие лимиты
- cleaner/TTL
- tmpfs вместо диска
- контроль конкуренции
- read-only код
- egress deny
- базовый FIM

Это уже **сильно более защищенная система**.

---

# Спринт 2 — “Изоляция и отказоустойчивость”
**Задача:** уменьшить blast radius и подготовить архитектуру к более строгой модели.

## 1) Разделить роли по сервисам
Минимально:
- frontend отдельно
- backend/generation отдельно
- Mongo отдельно
- monitoring/FIM отдельно

Если пока один хост:
- хотя бы отдельные контейнеры/сервисы
- разные пользователи/права
- разные network policies

**DoD**
- Компрометация фронта не даёт автоматически запись в backend storage/code

---

## 2) Linux-first окружение
Если production не на Linux — запланировать миграцию.  
Для этой security-модели Linux удобнее:
- tmpfs
- read-only mounts
- firewall rules
- container hardening
- no-new-privileges
- seccomp/apparmor

**DoD**
- Целевая production-платформа — Linux

---

## 3) Контейнеризация backend
- read-only root filesystem
- отдельный `tmpfs` mount для временных данных
- ограничение RAM/CPU
- `no-new-privileges`
- drop capabilities

**DoD**
- Backend живет в ограниченном runtime-контуре

---

## 4) Разделение frontend и backend по доступу
Идея:
- frontend можно держать как static build
- backend — private service за reverse proxy
- Mongo — вообще не публичная

**DoD**
- Только edge/proxy смотрит в интернет
- Backend и DB не exposed публично напрямую

---

## 5) Внешний heartbeat и независимые алерты
- Если FIM/agent перестал слать heartbeat — это тоже alert
- Алерты не должны зависеть от того же сервера, который мониторят

**DoD**
- Остановка агента или loss of heartbeat видны снаружи

---

## 6) DR/HA базового уровня
Если текущий сервер “умирает по тех. причинам”:
- frontend не должен падать обязательно вместе с generation backend
- backup/standby планы:
  - отдельный backend node
  - отдельный Mongo
  - внешний reverse proxy/LB при необходимости

**DoD**
- Есть понятный план восстановления при падении текущего сервера

---

## Результат спринта 2
Вы получаете:
- лучшую изоляцию
- меньше общих точек отказа
- более безопасное окружение для backend
- основу для дальнейшего ухода от persistence sensitive data

---

# Спринт 3 — “Убрать чувствительный payload из постоянного хранилища”
**Задача:** приблизиться к настоящей модели “не писать пользовательский текст на постоянный диск вообще”.

Это уже самый серьезный рефакторинг.

## 1) Разделить metadata и sensitive payload
### В БД оставить только metadata:
- jobId
- userId
- type
- status
- createdAt
- expiresAt
- errorCode
- maybe file sizes / technical flags

### Пользовательский текст хранить только ephemeral:
- process memory
- tmpfs
- Redis with TTL (если подходит)
- другой RAM-backed store

**DoD**
- Полный пользовательский текст больше не пишется в постоянную Mongo-модель

---

## 2) Переделать `persistAndGenerate`
Сейчас у вас логика завязана на `model.create([payload])`.

Нужно перейти к модели:
- persistent metadata job
- ephemeral payload storage
- генератор получает payload из ephemeral store
- после генерации payload удаляется сразу или живет только в пределах TTL

**DoD**
- `persistAndGenerate` больше не создает persistent document record с полным текстом

---

## 3) Перевести generation flow на memory-first
По возможности:
- generate DOCX в Buffer/stream
- PDF в RAM/tmpfs
- download из RAM/tmpfs
- по TTL/close — cleanup

Если какая-то библиотека требует filesystem:
- оставить только tmpfs, не обычный диск

**DoD**
- Постоянный диск не используется для пользовательских данных и документов

---

## 4) Убрать долгоживущие артефакты
- никаких JSON snapshots
- никаких debug DOCX
- никаких “на всякий случай” сохранений результата в БД/диск

**DoD**
- После cleanup не остается чувствительных артефактов в app storage и БД

---

## 5) Полный security review
После рефакторинга провести повторный аудит:
- request path
- memory path
- temp dirs
- DB traces
- logs
- backup policy
- restore policy
- incident response

**DoD**
- Есть подтверждение, что чувствительные данные не попадают в persistent layers

---

## Результат спринта 3
Это уже почти целевая модель:
- metadata можно хранить
- пользовательский текст и документы — только RAM/tmpfs
- cleanup строго по TTL/close
- persistent storage не содержит исходный текст

---

# Что критично обязательно, а что можно позже

## Обязательно в первую очередь
1. Лимит 1 MiB
2. Nginx buffering config
3. Безопасные логи
4. `expiresAt` + cleaner + early close
5. Один активный job на пользователя
6. `MAX_CONCURRENT_JOBS`
7. `storage/*` в tmpfs
8. Проверка PDF temp files
9. swap/core dump controls
10. read-only code/templates
11. no-root + egress deny

## Очень желательно во втором шаге
1. Внешний FIM
2. Разделение frontend/backend/DB
3. Linux/container hardening
4. Внешний heartbeat

## Серьезный рефакторинг
1. Убрать payload из Mongo
2. Переделать `persistAndGenerate`
3. Перейти на metadata + ephemeral payload
4. Memory-first generation flow

# Реалистичная оценка по вашей текущей архитектуре

## Можно сделать быстро:
- спринт 1 почти целиком
- часть спринта 2

## Потребует архитектурной переработки:
- спринт 3

Причина простая:
сейчас у вас генерация и lifecycle уже организованы неплохо, но они построены вокруг:
- файлов в `storage/*`
- job metadata в БД
- вероятно, payload-документов в моделях Mongo

То есть до “строго RAM-only” путь есть, но он не в один шаг.

# Что делать, если фронт и бэк сейчас на одном сервере
На ближайшем этапе это не блокер.

## Минимальный разумный план:
- оставить пока один сервер
- но логически/контейнерно разделить:
  - frontend
  - backend
  - db
  - monitoring
- backend максимально зажать по правам и сети

## Потом:
- frontend вынести отдельно
- backend generation вынести отдельно
- monitoring/FIM вынести отдельно
- БД держать отдельно и приватно

---

# Если сервер упадет “по тех. причинам”
## Да, разделение поможет.
Особенно если сделать так:
- frontend отдельно
- backend отдельно
- database отдельно

Тогда падение одного узла не обязательно роняет всё сразу.

Но это уже больше про **availability/operability**, чем про RAM-only security.
