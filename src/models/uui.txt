Backend v2 roadmap
Этап 1. Очередь задач — фундамент
Цель: вынести генерацию в устойчивый background pipeline.

Делать
Поднять Redis
Взять BullMQ
Разделить роли:
API server — принимает запрос, создаёт job
Worker — обрабатывает генерацию
Перевести генерацию на очередь:
create job
enqueue
worker processing
update status in DB
Статусы job
Зафиксировать enum:

js

queued
processing
rendering_docx
converting_pdf
validating_layout
ready
failed
expired
cleaned
cancelled
Поля GenerationJob
Добавить/нормализовать:

js

status
step
progress
error
startedAt
finishedAt
expiresAt
attempts
result
files
Пример:

js

{
  status: "processing",
  step: "converting_pdf",
  progress: 60,
  error: null
}
Что менять
startGeneration → только создаёт job и ставит в очередь
runGenerationJob → исполняется только worker’ом
cleanup оставить отдельным scheduler’ом
generation/update статусов делать централизованно
Результат этапа
API отвечает быстро
генерация не блокирует request lifecycle
можно ограничивать concurrency
можно делать retries
база под масштабирование готова
Этап 2. Realtime статусы
Цель: фронт получает живой статус job.

Рекомендация
Для твоего кейса сначала SSE, не WebSocket.

Почему
статусы идут только сервер → клиент
проще реализации и поддержки
меньше инфраструктурной сложности
для генерации документов этого обычно достаточно
Делать
endpoint:
GET /jobs/:id/events — SSE stream
endpoint:
GET /jobs/:id — текущее состояние
worker при смене статуса:
обновляет Mongo
публикует event
Источник событий
2 варианта:

через Redis pub/sub
через Mongo change streams
Рекомендую: Redis pub/sub, раз Redis уже будет из-за BullMQ.

События
js

job:queued
job:processing
job:progress
job:completed
job:failed
job:expired
job:cleaned
Результат этапа
фронт видит прогресс в реальном времени
можно показывать шаги генерации
можно уведомлять о готовности без polling
Этап 3. Production hardening
Цель: сделать систему устойчивой и обслуживаемой.

3.1 Startup checks
При старте проверять:

Mongo доступен
Redis доступен
LibreOffice доступен
storage папки существуют
шаблоны существуют
Если критично — не стартовать worker.

3.2 Единые paths
Сделать paths.js:

js

PROJECT_ROOT
STORAGE_ROOT
DOCX_DIR
PDF_DIR
ARMDOC_DIR
TEMPLATES_DIR
И убрать process.cwd() из критичных мест.

3.3 Template validation
На старте валидировать profiles:

все шаблоны существуют
для order существуют и order, и approval шаблоны
Если нет — логировать список проблем.

3.4 Structured logging
Поставить нормальный логгер:

pino или winston
Минимум логировать:

jobId
documentType
status
step
duration
error
3.5 Retry policy
На уровне очереди:

retries для временных ошибок
no retry для конфигурационных ошибок шаблонов
Разделить типы ошибок:

transient
permanent
3.6 Health endpoints
Добавить:

/health
/health/db
/health/redis
/health/storage
3.7 Cleanup hardening
Cleanup должен:

удалять только expired jobs
помечать cleaned
логировать failed cleanup
не удалять job, если файлы не удалились по серьёзной причине
Технический выбор
Брать
BullMQ
Redis
SSE
Pino
MongoDB оставить как есть
Не делать сразу
WebSocket, если нужен только job-status
свою самописную очередь
сложную оркестрацию микросервисов

Отвечает за:

Мой финальный совет
Если делаешь “надолго”, то правильный следующий шаг — не WebSocket сам по себе, а BullMQ + Redis + worker separation.

WebSocket/SSE без очереди — косметика.
Очередь без realtime — уже взрослая архитектура.
