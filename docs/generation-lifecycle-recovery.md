# Виправлення завислих генерацій — V2

Репозиторій: AlexRosly/armia-doc. База патча: 0345a4c9fe3152299a1f1e221383786bc7c9d183.
Локальна гілка: fix/generation-lifecycle-recovery.

## Що змінено

- Активна задача іншого типу або режиму повертає HTTP 409 з поясненням. Рапорт більше не отримує jobId старого акту.
- Нові inline-задачі записують ідентичність API-процесу. Якщо на тому самому Linux-хості підтверджено його зупинку, задача умовно переходить у failed. Перевірка виконується при створенні, читанні статусу та під час планового прибирання. Конкурентний перехід у ready зберігається.
- Старі задачі без записаного власника потребують перевірки адміністратором; повторне створення повертає пояснення замість мовчазного очікування.
- Прибирання за віком зберігає файли queued/processing і ще доступних ready-задач. Недоступність MongoDB не спричиняє видалення файлів з jobId.
- Redis-публікація прогресу використовує окреме з'єднання з обмеженим очікуванням команди (2 секунди). З'єднання BullMQ не змінюється.
- Прибрано schema-default layoutCheck=passed. Стан processing більше не видається за успішну перевірку верстки у статусній відповіді.
- Додано адресний інструмент відновлення старої задачі. Він не видаляє дані чи файли; звичайне прибирання файлів продовжує діяти окремо.

## Нове у V2

- Унікальний частковий індекс `one_active_generation_per_client` на clientId для queued/processing. Гарантію забезпечує MongoDB, зокрема між різними API-процесами. ready/failed звільняє місце автоматично через зміну статусу. Умова індексу містить активні задачі зі строковим clientId, включно зі старими без fingerprint. Legacy-записи без clientId або з null не входять до індексу.
- API намагається перевірити/створити індекс під час запуску; помилка індексу більше не зупиняє API. Створення задач також чекає підтвердження індексу. Якщо індекс неможливо створити, генерація не працює без блокування.
- Джерельний документ і задача створюються в одній транзакції. Запит, який програв гонку, відкочує свої записи, читає задачу переможця і не запускає генератор повторно.
- SHA-256 fingerprint у GenerationJob: ключі об'єктів сортуються; порядок масивів, текст, пробіли, пунктуація і типи чисел зберігаються. Лише кореневі _id/__v/createdAt/updatedAt виключені як серверні метадані. Вміст запиту і fingerprint не додаються у відповідь або логи.
- Ідентичний активний запит повертає existing:true; змінений — HTTP 409 ACTIVE_GENERATION_DATA_CONFLICT. Старий активний запис без fingerprint не порівнюється приблизно і не повертається мовчки: HTTP 409 ACTIVE_GENERATION_REQUIRES_REVIEW.

MongoDB має підтримувати транзакції (replica set, як і попередній код) і partialFilterExpression з $in: використовуйте MongoDB 6.0+ з відповідним FCV. Індекс управляється явно; не видаляйте його через syncIndexes або ручну міграцію під час роботи API.
Джерело правила partial unique index: https://www.mongodb.com/docs/manual/core/index-partial/ .

## Застосування патча

В архіві два варіанти — застосовуйте ЛИШЕ ОДИН:

- `backend-generation-lifecycle-v2-full.patch` — якщо попередній патч ще не встановлено, для базового коміту, зазначеного вище.
- `backend-generation-lifecycle-v1-to-v2.patch` — якщо наш попередній патч V1 уже встановлений без інших змін цих файлів.

Для оновлення V1 замініть назву full-патча в командах нижче на v1-to-v2. Не застосовуйте обидва.

Розпакуйте архів і покладіть backend-generation-lifecycle-v2-full.patch у корінь чистої копії репозиторію. Виконайте в ній:

```bash
git switch -c fix/generation-lifecycle-recovery
git apply --check backend-generation-lifecycle-v2-full.patch
git apply backend-generation-lifecycle-v2-full.patch
node --test tests/generation.lifecycle.test.js
git add server.js src scripts tests docs
git commit -m "Fix interrupted inline generation recovery and active job reuse"
git push -u origin fix/generation-lifecycle-recovery
```

Після push відкрийте PR у main. Якщо git apply --check повідомить конфлікт, не застосовуйте патч примусово: він підготовлений для зазначеної вище бази.

### Перед перезапуском API — обов'язково

Після оновлення файлів, з кореня серверного backend:

```bash
node scripts/check-active-generation-index.js
```

Це читання. Якщо знайдено групи дублікатів, адресно перевірте кожну задачу; не скидайте всю групу. Використовуйте recover-generation-job.js тільки для підтверджено перерваних задач. Інакше новий API продовжить роботу, але створення нових задач поверне HTTP 503.

Дочекайтеся завершення поточних генерацій. Потім встановіть індекс і перезапустіть API:

```bash
node scripts/check-active-generation-index.js --apply
pm2 restart 0
```

Перезапуск виконуйте лише якщо встановлення індексу завершилося успішно. Команда --apply створює індекс; вона не змінює статуси задач і не видаляє документи. Індекс також контролює ще запущений старий API, тому використовуйте вікно встановлення без активних генерацій. Відмова індексу через дублікати/версію MongoDB/права потребує виправлення причини, а не вимкнення перевірки. Залежності не змінені; QUEUE_ENABLED=false можна залишити.

Окремий інтеграційний тест перед rollout — лише на ТЕСТОВОМУ replica set:

```bash
MONGO_TEST_URI='mongodb://127.0.0.1:27017/?replicaSet=rs0' node --test tests/generation.admission.mongo.test.js
```

Тест створює випадкову тестову базу, запускає 20 паралельних однакових запитів, перевіряє одну задачу/один джерельний документ/один запуск, відмову зміненим даним і звільнення місця після ready. Тест видаляє тільки створену ним тестову базу. Без MONGO_TEST_URI він позначається SKIP. Локально його не виконано: MongoDB у цьому середовищі немає.

## Ваша стара задача

Після встановлення коду, з /home/deploy/apps/backend:

```bash
node scripts/recover-generation-job.js 6aa65bea0c6d3645ec88ee53
```

Це лише читання: покаже статус, тип, updatedAt та ознаку власника. Нічого не змінює.

Якщо задача досі queued/processing, адміністратор має підтвердити, що її вже не виконує жоден API, воркер або дочірній процес. Старі логи пов'язують її з PID 1306783; сама відсутність свіжих рядків у логу недостатня. Потім підставте точний updatedAt із попереднього виводу:

```bash
node scripts/recover-generation-job.js 6aa65bea0c6d3645ec88ee53 --apply --confirm-no-live-executor --expected-updated-at 'ТОЧНИЙ_UPDATED_AT_З_ВИВОДУ'
```

Команда адресно переведе задачу у failed, якщо статус і updatedAt не змінилися. Для queue-задач вона відмовить: їх слід спочатку узгодити з BullMQ. Для нових inline-задач відмовить, якщо зупинку власника неможливо підтвердити.

Після успіху поверніться у форму Brave й повторно натисніть створення. Переконайтеся, що create повертає новий jobId, статус переходить у ready або failed і файли завантажуються. Перезавантаження сторінки може втратити незбережені поля форми.

## Перевірка та межі

Локально пройшли 37 тестів node:test з підміною MongoDB, Redis та файлових операцій: власник живий/зупинений/PID повторно використаний, гонка з ready, конфлікти типу/режиму, захист прибирання, відмова публікації під час генерації та запобіжники адміністративної команди. Також перевіряється застосовність патча до базового коміту.

Реальний MongoDB/Redis/LibreOffice та production-генерація в цьому середовищі не запускалися. Після встановлення потрібен один наскрізний запуск документа.

Це захист життєвого циклу, а не оптимізація верстки. Він не перериває довгу, але живу генерацію. Автоматичне відновлення консервативне: одна Linux-машина, той самий UID і PID namespace; невідомі/віддалені власники не визнаються зупиненими. Старі legacy-задачі не скидаються автоматично лише за віком. Доставку завершення через SSE за втрати повідомлення потрібно окремо підстрахувати опитуванням на фронті.

## Фронт

Перевірено фронтенд на коміті 209b6282ba95bf265ea4e87ea85176ab2b2a07e6. Проксі для report/order/act зберігають статус і JSON беку; runGenerationJob читає message при неуспішній відповіді; усі три сторінки прибирають spinner, закривають модальне очікування і показують помилку, не скидаючи форму. Для нових 409 обов'язкової зміни фронту немає.

Для наступної UX-правки: зберігати jobId у стані сесії, дати кнопку «Переглянути поточний документ», а SSE підстрахувати періодичним читанням статусу. Не виконувати автоматичний повтор створення при 409 зі зміненими даними. Поточний патч не додає ці можливості на фронт.

Межа блокування — clientId сесії браузера. Інший браузер/нова cookie мають інше місце. Це не глобальне обмеження ресурсів і не обмеження на фізичну особу.

## Hotfix V2.1: доступність API при відмові індексу

Попередній V2 зупиняв увесь API при помилці createIndex і не показував подробиць через неправильний виклик logger.error. V2.1 залишає маршрути статусів/завантаження доступними, записує структуровану помилку індексу в серверний лог і повертає GENERATION_ADMISSION_UNAVAILABLE (503) для нових генерацій. Записи джерела/задачі не створюються без індексу. Точну причину помилки індексу потрібно усунути окремо; hotfix не відключає атомарне блокування.

Діагностична команда check-active-generation-index.js без --apply тепер показує версію MongoDB (якщо дозволено), наявні індекси та групи дублікатів без clientId і вмісту документів. Сам hotfix не змінює дані бази.

## Hotfix V2.2: legacy-записи без clientId

Діагностика підтвердила, що 8 старих активних задач згрупувалися за null, а не за ідентифікатором одного користувача. В умову часткового індексу додано clientId: { $type: "string" }. Preflight використовує ту саму умову з OPTIONS, тому він більше не видає ці legacy-записи за конфлікт сесії. Нові запити без непорожнього строкового clientId як і раніше отримують CLIENT_ID_REQUIRED до створення документів. Жоден старий запис не видаляється і не змінює статус.

За наданим переліком потрібного індексу ще немає: після застосування V2.2 виконайте node scripts/check-active-generation-index.js --apply. Не видаляйте звичайний clientId_1. Якщо в іншому середовищі вже є one_active_generation_per_client зі старою умовою, команда відмовить з конфліктом специфікації; hotfix навмисно не видаляє чинний індекс автоматично.
